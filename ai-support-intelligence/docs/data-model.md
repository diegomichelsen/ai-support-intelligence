# Data Model and Data Contract

## 1. Purpose

This document defines the initial data contract for AI Support Intelligence.

It establishes a consistent structure for support conversations, participants, messages, operational metrics, assignments, and conversation history.

It will guide the mock API, Python services, AI analysis, database persistence, automated tests, and dashboard.

## 2. Design Principles

- Use consistent field names across the system.
- Use unique identifiers for conversations, messages, participants, and events.
- Represent timestamps in ISO 8601 format with an explicit timezone.
- Store durations in seconds.
- Use `null` when a value is unknown, unavailable, or not applicable.
- Never use zero to represent missing data.
- Preserve original source data separately from AI-generated assessments.
- Use synthetic data only in the public repository.
- Document the source and calculation method of derived metrics.
- Do not infer unsupported operational metrics.
- Keep generated Cases separate from source conversation records.

## 3. Conversation Entity

Each conversation represents a customer support interaction.

### Required fields

| Field | Type | Description |
|---|---|---|
| `id` | string | Unique conversation identifier |
| `brand_id` | string | Identifier of the brand |
| `channel` | string | Origin channel, such as chat or email |
| `status` | string | Current conversation status |
| `created_at` | datetime | Conversation creation timestamp |
| `participants` | array | People and automated agents involved |
| `messages` | array | Conversation messages in chronological order |

### Optional fields

| Field | Type | Description |
|---|---|---|
| `brand_name` | string or null | Brand display name, when available |
| `category` | string or null | Category supplied by the source platform, when available |
| `closed_at` | datetime or null | Timestamp of the latest closure |
| `metrics` | object or null | Operational metrics associated with the conversation |
| `conversation_rating` | object or null | Original customer rating and related information |
| `assignment` | object or null | Assignment and closure attribution information |
| `reopen_history` | object or null | Reopening count and event history |

The `category` field represents source-provided information. Classifications generated by AI during monitoring must be stored separately as Cases.

## 4. Operational Metrics

Operational metrics are grouped under the `metrics` object.

| Field | Type | Description |
|---|---|---|
| `first_response_time_seconds` | integer or null | Time until the first qualifying human or automated response, according to the defined rule |
| `average_response_time_seconds` | number or null | Average qualifying response time |
| `resolution_time_seconds` | integer or null | Time to resolution under the defined calculation rule |
| `fcr` | boolean or null | Whether the conversation meets the defined first-contact resolution criteria |

Metric calculation rules must be documented before these values are used for performance reporting.

If a metric is supplied by the source platform, preserve its source provenance. If calculated internally, document the formula and source fields used.

Do not treat illustrative values in synthetic data as validated operational measurements.

## 5. Participants

Participants identify the entities involved in a conversation.

Each participant should contain:

- `id`: unique participant identifier.
- `type`: `customer`, `human_agent`, `ai_agent`, or `automation`.
- `name`: display name, when available.

The participant list must not be used as a substitute for message-level authorship.

## 6. Messages

Messages represent individual replies or conversation events.

Each message should contain:

- `id`: unique message identifier.
- `created_at`: timestamp of the message or event.
- `author_id`: identifier of the author, when applicable.
- `author_name`: display name of the author, when available.
- `author_type`: `customer`, `human_agent`, `ai_agent`, or `automation`.
- `message_type`: `message`, `note`, `system_event`, or another explicitly supported type.
- `body`: message content, when applicable.
- `attachments`: array of attachment metadata, defaulting to an empty array when none exist.

Messages must be ordered chronologically. System events must be distinguishable from customer-facing messages.

Each non-null `author_id` should reference a participant when the author is represented in the participant list.

## 7. Conversation Rating

The `conversation_rating` object may contain:

- `score`: original customer rating.
- `remark`: customer feedback, if available.
- `rated_at`: timestamp of the rating, if available.

The original rating must be preserved without modification.

Any later decision about whether a rating qualifies for conventional CSAT or Justified CSAT must be stored separately from the original rating.

The rating scale and validation rules must be defined before CSAT calculations are implemented.

## 8. Assignment

The optional `assignment` object contains assignment and closure attribution information.

It may contain:

- `admin_assignee_id`: identifier of the currently assigned human agent.
- `admin_assignee_name`: display name of the assigned human agent, when available.
- `team_assignee_id`: identifier of the currently assigned team.
- `team_assignee_name`: display name of the assigned team, when available.
- `count_assignments`: number of recorded assignment events, when known.
- `last_closed_by_id`: identifier of the actor who last closed the conversation.
- `last_closed_by_name`: display name of that actor, when available.

Identifiers should be the primary references. Names are display information and must not replace identifiers.

The meaning of `count_assignments`, including whether the initial assignment counts, must be defined before it is used in reporting.

## 9. Reopening History

The optional `reopen_history` object contains:

- `count_reopens`: number of recorded reopen events.
- `reopen_events`: array of reopening events.

Each reopening event should contain:

- `id`: unique event identifier.
- `occurred_at`: timestamp of the reopening.
- `actor_id`: identifier of the actor responsible, if known.
- `reason`: reason for reopening, if available.

When the event history is complete, `count_reopens` must equal the number of recorded reopening events.

If the history is incomplete, the count must not be presented as a verified total.

## 10. Data Quality Rules

- Identifiers must be unique within their defined entity scope.
- Timestamps must use a consistent timezone-aware format.
- Durations must not be negative.
- A closed conversation must have a valid `closed_at` timestamp.
- An open conversation may have `closed_at` set to `null`.
- Missing data must remain distinguishable from a measured value of zero.
- Metric values must follow their documented calculation or source rules.
- FCR must remain `null` when the available evidence is insufficient.
- Reopening and assignment counts must be consistent with their event histories when those histories are complete.
- Messages must be ordered chronologically.
- Original ratings and conversation content must not be overwritten by AI assessments.
- Optional fields must not be populated with invented values merely to complete a record.

## 11. Source Data, Derived Data, and AI Assessments

The system must distinguish three types of information:

1. **Source data:** fields received from the support platform or mock API.
2. **Derived operational metrics:** values calculated from source fields using documented rules.
3. **AI-generated assessments:** Cases, classifications, audit findings, explanations, and recommendations.

AI-generated assessments must include traceable references to the conversation or messages that support their conclusions.

Cases are generated during the monitoring process. They are not source conversation fields and must be stored separately from the original conversation record.

AI findings must never overwrite original conversation data.

## 12. Versioning and Change Management

Changes to field names, types, meanings, or validation rules must be documented.

Breaking changes to the data contract must be reviewed before being applied to the mock API, services, database, and tests.

## 13. Open Decisions

The following rules must be finalized before the corresponding features are implemented:

- Exact response-time calculation rules.
- Exact resolution-time calculation rules.
- First-contact resolution eligibility and calculation.
- Supported source channels and status values.
- Customer rating scale and validation.
- Treatment of reopened conversations in time-based metrics.
- Handling of incomplete event histories.
- Assignment count calculation rules.
- Data contract versioning strategy.
